# GPTQLinear 算子融合开发规划

## 1. 目标

当前 Qwen3 GPTQ-INT8 路径在 [src/myvllm/layers/gptq.py](../../src/myvllm/layers/gptq.py) 中采用 PyTorch reference 实现：每次 `GPTQLinear.forward()` 都解包 `INT32 qweight`，执行 zero point 和 scale 变换，生成完整 FP16 权重，再调用 `F.linear`。

阶段一的目标是让 kernel 直接消费 packed `qweight` 和 `scales`，在计算矩阵乘的过程中完成反量化，避免每次 forward 写出完整的 FP16 权重。当前 profile 已显示 decode 投影时间约 95% 用于反量化，下一步应先优化 decode。

本规划只针对 GPTQ 投影融合，不同时改造 attention、RMSNorm、SiLU、CUDA Graph 或多卡通信。每次只引入一个性能变量，最终以模型端到端结果决定是否启用。

## 2. 当前基线与约束

当前正式 baseline 记录在 [baseline.md](../../benchmark/qwen/qwen3-1.7B-gptq-INT8/stage1-results/baseline.md)：

| 指标 | 当前值 |
| --- | ---: |
| Decode 延迟 P50 | 157.13 ms/token |
| Decode 吞吐 P50 | 6.36 token/s |
| Prefill TTFT P50 | 220.44 ms |
| 峰值 allocated 显存 | 6.34 GiB |
| 峰值 reserved 显存 | 6.42 GiB |
| 测试形状 | batch 1，prompt 20 token |

投影 profile 记录在 [projection-profile.md](../../benchmark/qwen/qwen3-1.7B-gptq-INT8/stage1-results/projection-profile.md)。当前已经确认：

- decode 使用 `[1, 2048]` 和 `[1, 6144]` 两类输入形状；prefill 本轮使用 `[20, 2048]` 和 `[20, 6144]`。
- decode 每层 7 个投影的反量化中位数合计约 5.12 ms，矩阵乘约 0.25 ms。
- `gate_proj`、`up_proj`、`down_proj` 约占 decode 反量化时间的 80%，应优先覆盖这三种形状。
- 当前每次 forward 会产生约 4 MiB、8 MiB 或 24 MiB 的临时 FP16 权重。
- profile hooks 会显著增加端到端延迟，只用于归因，不能作为优化后的吞吐基线。

实现必须保持以下已验证限制：

- GPTQ INT8，`int32` packed weight，低字节优先。
- 每个 packed `int32` 包含 4 个量化值。
- zero point 固定为 128，group size 固定为 128。
- `qweight` 逻辑布局为 `[input_size / 4, output_size]`。
- `scales` 布局为 `[input_size / 128, output_size]`。
- 输出权重方向必须等价于 `F.linear` 使用的 `[output_size, input_size]`。
- 当前模型仍是单 GPU、FP16 activation、eager 执行。

## 3. 总体设计

保留当前实现为 `reference` 后端，增加可切换的融合后端。建议运行时后端至少包含：

```text
reference       每次反量化 + F.linear，正确性基准
fused_decode    packed qweight/scales + decode GEMV
fused_prefill  packed qweight/scales + prefill GEMM
```

后端选择属于运行时配置，不写入 checkpoint 的 `quantization_config`。默认值保持 `reference`，直到新后端完成正确性和端到端性能验收。

### 3.1 模式分派

不能只用输入 token 数量判断模式：batch 1 decode 和长度为 1 的 prefill 可能拥有相同的张量形状。

生产路径应使用已经存在的 `Context.is_prefill`：

- [model_runner.py](../../src/myvllm/engine/model_runner.py) 在准备输入时设置上下文。
- [context.py](../../src/myvllm/utils/context.py) 保存当前执行模式。
- `GPTQLinear` 根据显式上下文选择 `fused_decode` 或 `fused_prefill`。

单层 microbenchmark 和单元测试应提供显式模式参数或显式设置 context，不能依赖形状猜测。

## 4. 阶段 A：建立后端接口与 reference 回归

### 开发内容

- 在 `GPTQLinear` 中增加后端选择和统一 dispatch 入口。
- 保持当前 `dequantize_gptq_int8() + F.linear` 代码不变，作为 reference。
- 后端未加载、dtype 错误、unsupported shape 和非法 context 必须继续快速失败。
- 增加后端名称、输入形状和运行模式的诊断信息，便于 benchmark 确认实际执行路径。

### 验收

- 默认配置与当前 baseline 输出完全一致。
- reference 路径通过现有 `tests/test_gptq.py`。
- 不改变 dense Qwen3 路径和非量化模型行为。

## 5. 阶段 B：实现 decode fused GEMV

这是第一优先级。第一版只要求覆盖当前 Qwen3-1.7B 的真实投影形状：

| 投影 | 输入形状（decode） | 输出维度 |
| --- | --- | ---: |
| q/o | `[batch, 2048]` | 2048 |
| k/v | `[batch, 2048]` | 1024 |
| gate/up | `[batch, 2048]` | 6144 |
| down | `[batch, 6144]` | 2048 |

其中 `batch=1` 是首要目标，之后验证 batch 2 和 batch 4。kernel 必须直接读取 packed `qweight` 和 `scales`，不能在 forward 中生成 `[output, input]` 的完整 FP16 权重。

### 开发步骤

1. 先写独立 Triton wrapper 和最小 kernel，只支持 batch 1。
2. 实现低字节解包：对每个 `int32` 取 4 个 byte，减去 128。
3. 按输入行的 `input_index // 128` 读取 scale。
4. 在 tile 内完成反量化值与 activation 的乘加，使用与 reference 一致的累加精度和输出 dtype。
5. 覆盖 q/k/v/o/gate/up/down 的实际矩阵尺寸。
6. 增加 batch 2、4 的小 batch 路径；如果 batch 1 与小 batch 的最佳 tile 不同，可以保留两个配置。
7. 检查 kernel 是否产生完整 FP16 权重临时张量，以及是否有异常的 workspace 增长。

### 单层正确性测试

- 合成 packed weight 覆盖低字节优先、zero point 128、group size 128、多 group 和边界维度。
- 对同一输入比较 `reference` 和 `fused_decode` 的输出。
- 从真实 checkpoint 抽取 q、o、gate、down 等不同尺寸投影进行对照。
- 测试 batch 1、2、4，测试输入为 FP16，输出 shape 与 `F.linear` 一致。

## 6. 阶段 C：实现 prefill fused GEMM

decode kernel 稳定后，再实现 prefill 路径。prefill 输入 token 数较多，计算形态从 GEMV 转为 GEMM，不能直接假定 decode kernel 仍然最优。

### 首批形状

- `[20, hidden_size]`
- `[128, hidden_size]`
- `[512, hidden_size]`
- 对应的 down projection 输入维度 `[tokens, 6144]`

### 开发要求

- 使用适合多行输入的二维 tile。
- 直接消费 packed qweight 和 group scales。
- 保持输出布局和 reference 完全一致。
- 对长 prompt 检查临时显存和 workspace，避免因为融合计算引入新的大 buffer。
- 如果实测长 prompt 中矩阵乘已经占主导，可以单独调整 GEMM tile；不要为了统一代码强行复用 decode kernel。

## 7. 阶段 D：完整模型集成与验证

每个后端都按以下顺序验证：

1. packed 解包和 scale 计算测试。
2. 单层权重和线性输出测试。
3. 固定 token ID 的完整模型 hidden states/logits 对照。
4. 固定采样参数的生成 smoke test。
5. 端到端性能和显存测试。

完整模型对照至少记录：

- max absolute error
- relative error
- top-1 一致率
- KL divergence
- 必要时记录 hidden state error

生成文本相似不能替代 logits 对齐。任何 fused kernel 在 logits 对照通过前都不能成为默认后端。

## 8. 性能评估与默认启用条件

使用 [run_stage1.sh](../../benchmark/qwen/qwen3-1.7B-gptq-INT8/run_stage1.sh) 的相同 workload，分别运行 reference 和 fused 后端。正式性能测试不得开启 projection profiler。

每次记录：

| 类别 | 指标 |
| --- | --- |
| 初始化 | 模型加载时间、首次编译/warmup 时间 |
| Prefill | TTFT、prompt tokens/s、prefill 总延迟 |
| Decode | 单 token 延迟、tokens/s、P50/P90 |
| 端到端 | 总延迟、生成吞吐 |
| 显存 | peak allocated/reserved、KV cache blocks、workspace |
| 正确性 | logits/hidden states 误差和 top-1 一致率 |

建议使用至少 10 次正式迭代，baseline 和 fused 使用同一 GPU 状态、同一 checkpoint、同一 prompt token ID、同一 warmup 配置。

新后端只有在以下条件同时满足时才设为默认：

- 完整模型 logits 在约定 FP16 误差范围内一致。
- decode P50 有稳定的端到端改善，建议至少达到 10%。
- prefill、TTFT 和端到端延迟没有不可接受的回退。
- 峰值显存不超过目标机器可用范围，KV cache 容量没有被破坏。
- 重复运行结果稳定，收益不依赖首次编译或 profile hooks。

如果 kernel 只改善 projection microbenchmark 而没有改善端到端 decode，继续保留 reference 为默认，并记录未达到默认启用条件的原因。

## 10. 暂不纳入本规划的内容

- 完整 FP16 权重缓存：当前峰值已约 6.34 GiB，8GB 卡剩余空间不足以假设完整缓存可行；如需诊断，只做单层缓存 microbenchmark。
- QKV 或 gate/up 的跨投影融合：必须在单投影 fused kernel 正确且收益明确后再评估，否则会同时引入 packed layout、输出拼接和误差定位复杂度。
- CUDA Graph：当前 GPTQ 配置要求 eager，应在 fused kernel 稳定后单独验证。
- 多卡 GPTQ：涉及量化权重切分、group 边界和通信，属于独立的并行化工作。
