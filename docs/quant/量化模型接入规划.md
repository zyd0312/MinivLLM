# Qwen3-1.7B GPTQ-INT8 接入实现详解

本文说明当前 MinivLLM 对 Qwen3-1.7B-GPTQ-Int8 的实际接入方式。内容以仓库现有代码和 checkpoint 的真实格式为准，描述已经落地的配置解析、模型构造、权重加载和推理流程；文末单独列出当前限制与后续工作。

## 1. 支持范围和入口

当前接入针对本地 checkpoint：

    ~/project/LLM/models/qwen/Qwen3-1.7B-GPTQ-Int8

首版支持范围是 Qwen3ForCausalLM、GPTQ INT8、单 GPU、FP16 激活和 eager 执行。量化层使用 PyTorch reference 实现，没有新增专用 CUDA/Triton kernel。量化模型仍通过引擎原有的 generate、调度器、KV cache 和采样接口运行，执行层没有另起一套量化推理 API。

显式运行量化模型的命令是：

    uv run python main.py \
      --model-path ~/project/LLM/models/qwen/Qwen3-1.7B-GPTQ-Int8 \
      --quantization gptq

main.py 增加了 --model-path 和 --quantization gptq 两个可选参数。未传参数时仍沿用原有入口和配置字典；量化配置只有在显式选择 gptq 时才会触发。实际使用时应显式传入上面的模型路径和量化选项，避免把普通模型路径与量化模型配置混用。

调用链如下：

    main.py
      -> Config(run_config)
      -> _load_quantization_config(config, "gptq")
      -> LLMEngine
      -> ModelRunner
      -> Qwen3ForCausalLM(quant_config=GPTQConfig)
      -> GPTQLinear.forward()
      -> compute_logits() / sampler

## 2. 目标 checkpoint 的实际格式

配置和 safetensors header 已按目标目录核对。config.json 的关键字段如下：

| 项目 | 实际值 | 代码中的用途 |
| --- | --- | --- |
| 架构 | Qwen3ForCausalLM / qwen3 | 只构造 Qwen3 量化路径 |
| vocab size | 151936 | embedding 和 logits |
| hidden size | 2048 | Transformer 隐藏维度 |
| 层数 | 28 | decoder layer 数量 |
| attention heads | 16 | Q 头数量 |
| KV heads | 8 | GQA 的 K/V 头数量 |
| head dim | 128 | 每个 attention head 的维度 |
| intermediate size | 6144 | MLP 中间维度 |
| RoPE | rope_theta=1000000 | rotary embedding |
| 最大位置 | 40960 | RoPE 上限；运行配置另限制为不超过 32768 |
| dtype | float16 | 未量化参数、激活和 KV cache |
| embedding | tie_word_embeddings=true | lm_head 与 embedding 共享权重 |
| GPTQ | bits 8、group size 128、desc_act=false、sym=true | 只接受此布局 |
| packed dtype | int32 | 每个 int32 包含 4 个 INT8 值 |
| lm head | lm_head=false | lm head 保持 FP16 tied embedding |

checkpoint 是一个 safetensors 文件，共 898 个张量：114 个 FP16 参数和 196 个 GPTQ 投影。28 层的每层 7 个量化投影分别是 q_proj、k_proj、v_proj、o_proj、gate_proj、up_proj、down_proj。Embedding、各类 norm 和最终共享权重属于 FP16 参数。

量化投影的 checkpoint 张量组为：

    <projection>.qweight   int32
    <projection>.qzeros    int32
    <projection>.scales    float16
    <projection>.g_idx     int32

其中 qweight 沿输入维打包，低字节优先，每个 int32 存 4 个 8-bit 量化值；scales 的形状是 [input_features / 128, output_features]。全部真实投影的 g_idx 都满足 g_idx[i] == i // 128。qzeros 的每个 packed byte 都是 0x7f，对应实际 zero point 128。当前实现只接受这些已验证的 GPTQModel 2.2.0 约定。

典型形状如下，线性层逻辑方向为 [output, input]：

| 投影 | input -> output | qweight | qzeros | scales |
| --- | ---: | ---: | ---: | ---: |
| q_proj | 2048 -> 2048 | [512, 2048] | [16, 512] | [16, 2048] |
| k_proj / v_proj | 2048 -> 1024 | [512, 1024] | [16, 256] | [16, 1024] |
| o_proj | 2048 -> 2048 | [512, 2048] | [16, 512] | [16, 2048] |
| gate_proj / up_proj | 2048 -> 6144 | [512, 6144] | [16, 1536] | [16, 6144] |
| down_proj | 6144 -> 2048 | [1536, 2048] | [48, 512] | [48, 2048] |

## 3. 配置解析：通用 Config 与 GPTQ 后端分工

配置入口在 src/myvllm/config.py。Config 继承 dict，因此保留原有 config['key']、config.get() 和进程间 pickle 的使用方式。它不主动猜测模型是否量化，也不会在普通配置下打开 checkpoint 的 config.json。

当调用方显式传入 quantization='gptq'，或者字典中带有该选择时，Config 才调用 src/myvllm/utils/quant_config.py 的 _load_quantization_config：

1. 根据 model_name_or_path/config.json 定位模型配置。
2. 读取并校验 quantization_config。
3. 校验 model_type=qwen3、架构、FP16、tied embedding、无 attention bias、SiLU、无 RoPE scaling 和单卡 eager 运行条件。
4. 将 Hugging Face 字段映射成项目字段，例如 hidden_size、num_heads、num_kv_heads、num_layers、base、max_position。
5. 从 generation_config.json 读取 EOS；目标模型的 EOS 是 [151645, 151643]。
6. 返回派生字段和 GPTQConfig，由 Config 合并到自身字典。

GPTQConfig 是轻量数据类，保存 bits、group size、desc_act、sym、pack dtype、checkpoint format、quant method 和 lm head 标记。from_dict() 要求这些字段完整存在；__post_init__() 只接受当前后端实现过的值。这样 GPTQ 特有的文件读取、格式校验和模型字段映射都集中在 quant_config.py，通用 Config 只负责调用后端并合并结果。

配置解析不会在 worker 进程反序列化时重复读取 checkpoint。LLMEngine 收到普通字典时才自动包装成 Config；已经是 Config 的对象直接复用。

## 4. Qwen3 模型构造

src/myvllm/engine/model_runner.py 根据 quantization_config 是否存在选择 Qwen3 构造参数。量化模型在创建模型时就建立 GPTQ 投影，不先分配完整 FP16 dense 权重再替换。模型 dtype 明确设为 torch.float16。

src/myvllm/models/qwen3.py 保留 dense 和量化两条构造路径：

- dense 路径继续使用原有融合的 QKV 和 gate/up 投影，保持既有模型行为。
- 量化 attention 创建独立的 q_proj、k_proj、v_proj 和 o_proj。forward 分别计算后按 Q、K、V 顺序拼接，再进入 Qwen3 的 Q/K norm、RoPE、attention 和输出投影。
- 量化 MLP 创建独立的 gate_proj、up_proj 和 down_proj。gate 与 up 的结果拼接后执行现有 SiLU 门控，再调用 down projection。
- embedding、Q/K norm、输入 norm、post-attention norm、最终 norm 和 tied lm_head 保持 FP16。

量化路径要求 world_size == 1 且 projection 无 bias。这样可以直接匹配该 checkpoint 的键名和 packed shape，不需要在量化权重上复用 dense 层的融合或 tensor parallel 切片逻辑。模型顶层的 forward() 仍只返回 hidden states，compute_logits() 仍负责调用 lm head。

## 5. GPTQLinear 的实现

实现位于 src/myvllm/layers/gptq.py。这是一个单设备、PyTorch reference backend：

1. 构造时只分配 int32 qweight 和 FP16 scales buffer；不会分配等尺寸的 FP16 dense weight。
2. loader 写入 qweight 和 scales 后设置 _loaded=True；未加载或校验失败时 forward 立即报错。
3. dequantize_gptq_int8() 用位移和掩码按低字节到高字节解包 8-bit 值。
4. 将量化值减去固定 zero point 128，按输入行的 i // 128 选择 group scale。
5. 将结果重排成 [output, input] 的 FP16 权重，交给 torch.nn.functional.linear。

反量化公式是：

    W[out, in] = (unpack(qweight)[in, out] - 128)
                 * scales[in // 128, out]

输入和输出接口与普通线性层一致：激活为 FP16，输出为 FP16。当前实现每次 forward 都临时解包一层权重，因此优先保证格式和数值正确，decode 阶段会重复付出解包开销；这也是后续 fused kernel 优化的主要位置。接入本模型本身不需要新增 kernel。

## 6. 严格权重加载

量化加载逻辑位于 src/myvllm/utils/loader.py 的 _load_gptq_checkpoint()，入口签名仍是 load_weights_from_checkpoint(model, path)。当模型带有 quant_config 时，loader 走 GPTQ 分支；普通模型仍走原有 dense 分支。

GPTQ 分支的流程是：

1. 读取 checkpoint config.json，构造 GPTQConfig，并与模型上的配置比较。
2. 扫描所有 safetensors header，建立张量名到文件的索引；发现重复张量名立即失败。
3. 根据模型参数和每个 GPTQLinear.checkpoint_shapes() 生成期望张量集合。
4. 对比 checkpoint 实际集合，任何缺失或多余张量都报错，避免随机初始化或静默跳过。
5. 在 safe_open 上下文中逐张量读取，检查 dtype、shape 和 FP16 参数。
6. 对每个量化投影成组读取 qweight、qzeros、scales、g_idx，检查 qzeros 的 0x7f 编码、连续 128 分组和正的有限 scales，然后复制 qweight/scales。
7. 关闭 safetensors handle，确认全部期望张量均已加载，打印 FP16 参数和 GPTQ 投影数量。

真实 checkpoint 的验证结果是 114 个 FP16 参数、196 个 GPTQ 投影、898 个张量全部通过。tied embedding 下不要求额外的 lm_head.weight，因为模型顶层已经把 lm head 权重指向 embedding 参数。

## 7. 统一 execute/forward 路径

量化模型没有单独的 execute 接口。ModelRunner.run() 仍按原流程准备 prefill/decode 输入、调用 run_model()、在 rank 0 采样并重置上下文。run_model() 在 eager 路径中执行：

    hidden_states = self.model(input_ids)
    logits = self.model.compute_logits(hidden_states)

因此 GPTQ 只在 Qwen3 projection 内部改变权重表示；调度器、Paged KV cache、EOS 判断和生成 API 不需要知道 GPTQ packed 格式。KV cache 按 FP16 分配，量化权重的 int32 存储不会改变 attention 的 K/V 接口。

调度器现在把 EOS 标准化为集合，既兼容单个整数，也能处理 generation config 的 EOS 列表，并以 token_id in eos_ids 判断结束。目标模型的 generation_config.json 还包含 temperature 0.6、top-k 20、top-p 0.95；当前采样器实际使用 temperature，top-k/top-p 尚未实现。

## 8. 验证记录

已完成以下验证：

- tests/test_gptq.py：10 项通过，覆盖配置读取边界、GPTQ 配置校验、低字节优先解包、zero point、group index 和未加载保护。
- compileall：源码编译检查通过。
- git diff --check：文档和代码 diff 无空白错误。
- 真实 checkpoint：898 个张量集合、shape、dtype、qzeros、g_idx 和 scales 校验通过。
- 端到端 GPU smoke test：完成模型加载、prefill、decode 和文本输出。运行日志包含 Loaded and validated 114 FP16 tensors and 196 GPTQ projections，随后完成多轮 decode。

端到端生成成功说明当前接入链路可运行，不等同于已经完成与 Hugging Face/GPTQModel 参考实现的逐 token logits 对齐。当前仍应把独立反量化权重和参考实现对照作为数值正确性验收。

## 9. 当前限制和后续工作

当前实现明确限制为：

- 只支持上述 GPTQ INT8 配置、Qwen3 架构和目标 packed layout；不支持其它 bit 数、group size、动态 per-module 配置或 activation-order。
- 只支持单 GPU；尚未实现 GPTQ 权重的 tensor parallel 切分。
- 使用 PyTorch 逐层反量化加 F.linear，没有 fused CUDA/Triton kernel，decode 性能和显存临时开销仍需优化。
- 量化路径要求 eager；CUDA Graph 尚未作为量化后端验收。
- 当前采样器没有实现 checkpoint generation config 中的 top-k/top-p。
- 还没有完整的真实 checkpoint 与可信 GPTQModel/Hugging Face 参考 logits 对照报告。
- loader 首版重点覆盖当前单 safetensors 文件；多 shard index 的通用化仍可后续补充。

后续开发应按以下顺序进行：先完成真实权重的逐层/逐 token logits 对照，再针对 profiling 结果实现直接消费 packed 权重的 fused kernel；之后再设计满足 group size 和 packed 边界约束的多卡切分，并单独验证 CUDA Graph 与更完整的采样参数。
