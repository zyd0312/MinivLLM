# MinivLLM 推理优化规划

## 目标与决策

当前已接入 Qwen3-1.7B GPTQ-INT8，并能在单张 8GB RTX 5060 上完成模型加载和生成。下一阶段优先在这台机器上把正确性、性能基线和量化推理路径做扎实，再决定是否迁移到单机多卡扩展。优先级来自当前代码的实际瓶颈和已有硬件，不以实现功能数量作为目标。

主线建议是：

1. 建立可重复的正确性与性能基线。
2. 优化 GPTQLinear 的 decode 路径，重点评估反量化与矩阵乘融合。
3. 依据 profile 优化 Qwen3 共用的 attention 和算子路径。
4. 在 eager 路径稳定后评估 CUDA Graph。
5. 再评估 Speculative Decoding；多卡、KV Offload 和 DeepSeek 作为有明确需求时的扩展方向。

这里的“单卡优先”是项目当前最容易验证和形成性能证据的工程选择。若目标部署已经明确要求多卡、单卡放不下模型，或者研究重点是分布式并行，则应调整优先级，先完成多卡正确性与权重切分。

## 当前实现边界

| 范围 | 当前状态 | 对优化工作的影响 |
| --- | --- | --- |
| Qwen3 GPTQ-INT8 | 单 GPU、FP16 激活、eager；支持目标 GPTQ checkpoint 格式 | 量化多卡和 CUDA Graph 尚未支持 |
| GPTQLinear | forward 时解包 INT32、执行 zero point/scale 反量化，再调用 PyTorch F.linear | decode 每生成一个 token 都会重复做各层反量化，是首要 profile 对象 |
| Qwen3 projection | GPTQ 路径分别执行 Q/K/V 和 gate/up 投影 | 投影当前未融合；融合与 kernel 设计需结合 prefill/decode 分开评估 |
| Attention | 项目内有 Triton prefill 和 paged decode 实现 | 需要先验证正确性、长上下文和目标 GPU 上的性能，再决定优化点 |
| norm/activation | RMSNorm 与 SiLU 门控含 torch.compile 路径 | 不能仅凭减少算子调用推断有收益，应使用端到端 profile |
| 多卡 | dense 层含部分 Tensor Parallel 原语；GPTQ 配置明确拒绝 world_size 大于 1 | dense checkpoint 加载和完整四卡端到端流程仍需验证；不能只改 world_size |
| 服务入口 | 有常驻 FastAPI 包装示例；当前引擎不是线程安全的，服务以单 worker 和串行请求为前提 | 性能实验应先使用直接引擎调用，避免 HTTP 开销干扰 kernel 比较 |

## 阶段 0：建立可信基线

### 工作内容

- 固定模型 checkpoint、prompt/token ID、采样参数、上下文长度、batch size、GPU 功耗/时钟状态和软件版本。
- 为 Qwen3 GPTQ 建立专用 benchmark，区分模型加载、首次编译、warmup 和正式测量。
- 分别测 prefill 与 decode；decode 至少记录单请求 tokens/s 和逐 token 延迟，prefill 记录 prompt tokens/s 与首 token 延迟。
- 记录 GPU 峰值 allocated/reserved 显存、KV cache block 数和运行失败条件。
- 对比模型 hidden states/logits 与可信 Transformers + GPTQModel 参考结果；固定输入 token，报告 max absolute error、relative error、top-1 一致率，必要时再测 KL divergence。
- 每项性能至少多轮运行，报告中位数和离散程度；使用 CUDA event 或显式 synchronize，避免只测到异步 launch 时间。

### 交付与验收

- 增加一份可重复运行的 benchmark 命令和结果记录模板。
- 记录 eager GPTQ 基线、单卡 dense Qwen3 可运行状态（若模型和显存允许）以及参考实现的数值误差。
- 任何优化必须先通过数值正确性测试，再比较端到端指标。生成文本相似不能代替 logits 对齐。

当前 `benchmark_tps.py` 中的模型配置、输出长度和不同框架执行选项需要先统一，才能作为正式对照结果；现有 benchmark 不能直接充当优化前基线。

## 阶段 1：优化 GPTQLinear decode

这是当前最贴近已接入工作的方向，也是建议首先投入实现的性能工作。

### 1.1 分析并区分 prefill/decode

Prefill 通常对多个 token 做较大的矩阵乘，decode 通常每次只有少量 token，接近 GEMV。两种形状对带宽、并行度、launch 开销的要求不同；不要假设一个通用 kernel 同时最优。

对真实 Qwen3 各类投影采集以下 profile：输入 token 数、输出维度、反量化耗时、矩阵乘耗时、临时显存和总 forward 耗时。至少覆盖 q/k/v/o、gate/up、down 投影，以及 prompt prefill 和单 token decode。

### 1.2 建立后端对照

先保留当前 PyTorch reference 路径作为正确性基准，再实现可选后端：

- 低风险对照：模型加载后把量化权重反量化并缓存为 FP16，forward 直接做 F.linear。它会提高常驻显存，但能量化“重复解包”成本。
- 性能目标：Triton fused dequantization + GEMV/GEMM，在计算中消费 packed qweight 和 scales，避免每次 forward 写出完整反量化权重。
- 视实测决定是否保留两种 kernel：decode 使用 GEMV 形态，prefill 使用适合多 token 的 GEMM 形态。

缓存路径是诊断和可选后端，不预设它一定适合 8GB 卡。必须把权重缓存、KV cache 和 workspace 的共同显存占用纳入比较。

### 验收标准

- 合成测试覆盖 INT32 低字节优先解包、zero point 128、group size 128、边界和输出方向。
- 从真实 checkpoint 抽取投影，对照 reference 权重及线性输出。
- 各后端在 FP16 误差容限内匹配 reference，并通过完整模型 logits 对照。
- 同一 GPU、同一输入形状报告 prefill 和 decode 延迟、端到端 tokens/s、峰值显存；明确列出首次编译时间与稳定运行时间。
- 只有端到端生成指标有可重复改善且显存仍满足目标场景，才把新后端设为默认。

## 阶段 2：按 profile 优化 Qwen3 共用路径

优先检查下面这些位置，依 profile 中的耗时排序实施，而不是一开始并行改造多个算子：

1. Paged attention decode：确认跨 block 读取、GQA head 映射、上下文长度和 mask 的正确性；基准覆盖短到长上下文和不同 batch。
2. Prefill attention：比较当前 Triton 路径与可用的 PyTorch/SDPA 参考，检查长序列正确性和显存峰值。
3. residual + RMSNorm：当前 decoder 先做残差加法，再进入编译的 RMSNorm 路径。可测试融合 kernel，评估减少读写和 kernel launch 是否改善整层耗时。
4. SiLU + Mul：当前已通过 torch.compile；先测实际 shape 的编译结果，再判断手写 Triton 是否值得维护。
5. 量化模型独立 Q/K/V 与 gate/up 投影：如果 fused GPTQ kernel 尚不能覆盖多个投影，先以正确性和吞吐数据评估投影合并的收益与 packed layout 复杂度。

每次只引入一个优化变量。算子级 microbenchmark 用于解释结果，最终验收以模型端到端数据为准。建议至少报告单请求 decode、短 prompt TTFT、长 prompt prefill 速度和小 batch 吞吐。

## 阶段 3：验证 CUDA Graph

量化配置目前要求 `enforce_eager=True`，因此 CUDA Graph 是独立阶段，不能与首轮 kernel 改动混在一起。

开始前先检查 `ModelRunner.capture_cudagraph()` 的输入输出 buffer 形状、batch size 配置键和量化临时张量生命周期。捕获及 replay 必须覆盖 GPTQ layer 的反量化/计算操作，不能在捕获期间发生不允许的动态分配或控制流。

通过条件：eager 与 graph 的固定输入 logits 在误差容限内一致；覆盖 batch size 1 及常用 decode batch；重复 replay 不增长显存且无 graph capture 错误；端到端 decode 延迟相对 eager 有稳定改善。若收益不明显，保持 eager 是合理结果。

## 阶段 4：评估 Speculative Decoding

在 target 模型性能基线和数值行为稳定后，再实现 speculative decoding。它适合减少自回归串行步数，但需要 draft 模型、批量验证、接受/拒绝逻辑和 KV cache 回滚，改动涉及 `Sequence`、`Scheduler`、`ModelRunner` 和 cache 管理，不只是增加一个小模型调用。

建议先选一个可在单张 8GB GPU 同时驻留的轻量 draft/target 组合，再测 draft token 数、接受率、额外显存、单请求延迟和 tokens/s。若双模型挤占 KV cache 导致上下文或并发显著下降，应调整模型组合或暂缓该方向。

正确性验收应验证 speculative sampling 与 target-only sampling 的输出分布一致，而不是只检查常见 prompt 的文字看起来相同。报告需同时给出平均接受长度、加速比和显存增量。

## 阶段 5：多卡扩展的触发条件和工作范围

只有当模型无法放入单卡、目标需要更长上下文/更高并发，或项目目标明确转向分布式推理时，才将单机多卡提升为主线。多卡不是把 `world_size` 改成 4：

- Dense Qwen3：检查 checkpoint 加载是否调用并行层的 `weight_loader`，逐 rank 校验参数分片，并对齐单卡 logits。
- GPTQ Qwen3：实现 qweight、scales 等量化权重切分，处理 q/k/v head 分配、输入维 group size 128 和 int32 packing 边界；实现前向通信与 checkpoint 分片加载。
- 运行时：验证 NCCL 初始化、worker 退出清理、KV cache 每 rank 容量、batch 调度和通信开销。
- 性能：比较单卡与多卡吞吐和单请求延迟。小模型在多卡上的通信成本可能超过并行收益。

建议先验证 dense TP 端到端，再单独设计 GPTQ TP。当前 GPTQ 路径显式要求 `world_size == 1`，不能将其描述为已支持四卡。

## 暂缓方向

### KV Offload

KV Offload 解决的是显存容量和长上下文问题，涉及 CPU pinned memory、异步搬运、cache block 状态、attention 侧分层读取和传输调度。在单张 8GB 卡上它可能扩大可运行上下文，但可能降低 decode 速度。只有当测量确认主要限制是 KV cache 容量，且长上下文是明确目标时再做。

### DeepSeek 接入

完整 DeepSeek-V3 包含 MLA、MoE 和大规模专家权重，在本地 8GB 卡上难以完成有代表性的端到端验证。若未来目标是架构扩展，可选一个适合硬件的 DeepSeek Lite/MoE checkpoint，限定实现范围并保留正确性和性能验收；不建议当前用无法端到端运行的超大模型作为主线。

## 方向选择速查

| 目标 | 建议方向 | 当前优先级 |
| --- | --- | --- |
| 让已接入模型更快，且本机能完整测量 | GPTQ fused kernel、attention 和 profile 驱动的算子优化 | 最高 |
| 减少逐 token decode 步数 | Speculative Decoding | 单卡性能主线之后 |
| 模型或 KV cache 放不进单卡 | 多卡 TP 或 KV Offload，先按容量瓶颈选择 | 需求触发 |
| 展示新模型结构适配 | 小型 DeepSeek Lite/MoE | 后续探索 |

## 结果记录模板

每次优化都记录以下信息，避免只保留一个“加速百分比”：

| 项目 | 记录内容 |
| --- | --- |
| 运行环境 | GPU 型号与显存、驱动/CUDA、PyTorch、Triton、代码版本 |
| 模型 | checkpoint、量化格式、dtype |
| 输入 | prompt token 数、batch size、生成长度、采样配置 |
| 正确性 | max absolute/relative error、top-1 一致率、完整模型是否通过 |
| 性能 | 加载时间、TTFT、prefill tokens/s、decode tokens/s、端到端延迟 |
| 显存 | 峰值 allocated/reserved、KV cache token/block 容量 |
| 测量方法 | warmup 次数、迭代次数、统计值、是否包含编译和同步 |
| 结果 | 相对基线变化、失败条件、是否达到默认启用标准 |
