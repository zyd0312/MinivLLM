# MinivLLM 项目优化实录

本文按实际开发顺序记录 MinivLLM 的模型接入和推理优化工作。每条记录说明当时的问题、改动方案、这样设计的原因、验证结果和当前限制，便于之后复盘实现过程、准备项目总结或继续优化。

## 项目目标与当前范围

项目基于已有的 MinivLLM 推理引擎，完成 Qwen3-1.7B GPTQ-INT8 模型接入，并在单张 NVIDIA GeForce RTX 5060 Laptop GPU 上对 GPTQ 投影路径进行融合优化。当前优化聚焦于单 GPU、FP16 activation、eager 执行和一类实际 GPTQ checkpoint 格式；正确性通过后再用同一 workload 比较优化前后的端到端性能。

## 改进记录

### 记录一：接入 Qwen3 GPTQ-INT8

- 时间：2026-10-17
- 提交：`3dd82ef` `feat:量化qwen3模型接入`
- 主要代码：[quant_config.py](../../src/myvllm/utils/quant_config.py)、[loader.py](../../src/myvllm/utils/loader.py)、[gptq.py](../../src/myvllm/layers/gptq.py)、[qwen3.py](../../src/myvllm/models/qwen3.py)、[model_runner.py](../../src/myvllm/engine/model_runner.py)

**遇到的问题**

MinivLLM 原有模型加载路径面向普通浮点权重，无法直接解释 GPTQ checkpoint 中的 packed INT32 权重、scale、zero-point 和分组索引。Qwen3 GPTQ 也不能只通过把模型 dtype 改成 FP16 来加载：量化投影的参数名称、形状和语义都与普通 Linear 不同。

**改动内容**

- 增加 `GPTQConfig` 和量化配置入口，从 checkpoint 配置中识别量化格式，并对模型架构、位宽、group size、设备数、eager 模式和 embedding/head 等前提做校验。
- 实现 `GPTQLinear` reference 路径。packed INT32 每个元素按低字节优先装入 4 个量化值；前向时按 zero point 128 和 group scale 还原权重，再调用 `F.linear`。
- 扩展 Qwen3 模型结构，在 attention 的 Q/K/V/O 投影及 MLP 的 gate/up/down 投影中使用 GPTQLinear；embedding、norm 等其余权重仍按 FP16 加载。
- 为 GPTQ checkpoint 增加严格的 safetensors 加载和校验：检查预期 tensor 集合、shape、dtype、`qzeros`、`g_idx` 和 scales，避免格式不匹配时悄悄得到错误输出。
- 让引擎用 FP16 建立量化模型和 KV cache，并保留原有非量化模型创建路径。
- 增加配置、解包、checkpoint 校验和 GPTQLinear 相关测试。

**为什么这样改**

先实现清楚、可检查的 reference 路径，能够把“checkpoint 是否正确加载”和“自定义 kernel 是否计算正确”分开排查。格式校验有意限定到当前真实 checkpoint，而不是声称支持所有 GPTQ 变体；这样可以避免对不同 packing、zero-point 或 group layout 做错误假设。每次前向临时反量化单个投影，避免常驻完整 FP16 权重，适合显存有限的单卡验证。

**结果与当前边界**

Qwen3-1.7B GPTQ-INT8 已能在单张 RTX 5060 Laptop GPU 上完成加载和生成，并作为后续性能优化的可运行对象。reference 的端到端基线见后续记录。

目前接入范围是 Qwen3 `Qwen3ForCausalLM` 的特定 GPTQ-INT8 checkpoint：INT32 packing、group size 128、对称 zero point 128、FP16 activation/scales、单 GPU、eager 模式。尚不代表支持任意 GPTQ 格式、量化 lm_head、GPTQ tensor parallel 或 CUDA Graph。

**复盘要点**

量化格式本身就是模型接口的一部分。模型结构、权重命名和量化元数据必须一并校验；否则“模型能启动”并不能说明权重被正确解释。reference 实现的价值不仅是先跑通模型，也是后续 kernel 数值对照的基准。

### 记录二：建立 GPTQ 专用基线和投影 profile

- 时间：2026-10-18
- 提交：`381849a` `feat:benchmark测试`
- 主要代码：[benchmark.py](../../benchmark/qwen/qwen3-1.7B-gptq-INT8/performance/benchmark.py)、[run_stage1.sh](../../benchmark/qwen/qwen3-1.7B-gptq-INT8/performance/run_stage1.sh)
- 结果：[reference baseline](../../benchmark/qwen/qwen3-1.7B-gptq-INT8/results/performance/legacy-reference/run-20261018T055705Z/baseline.md)、[reference projection profile](../../benchmark/qwen/qwen3-1.7B-gptq-INT8/results/operator-profile/legacy-reference/run-20261018T055819Z/projection-profile.md)

**遇到的问题**

只观察生成速度无法区分模型加载、首次 warmup、prefill、decode 和 GPTQ 投影各自的开销。更重要的是，profile hook 会改变运行时间；若把带 profiler 的结果当作正式速度，优化前后的比较会失真。

**改动内容**

- 新增 Qwen3 GPTQ 专用 benchmark，固定 prompt、采样设置和生成长度，区分加载、首次 warmup 和正式迭代。
- 记录 TTFT、prefill 吞吐、decode 单 token 延迟与吞吐、端到端时延、峰值显存和 KV cache 容量，并保存 token IDs 与逐轮数据。
- 为 q/k/v/o/gate/up/down 投影记录反量化、矩阵乘、总 forward 和临时权重显存。
- 用独立进程运行 reference 性能基线和带 hook 的 projection profile，避免 profile 计时混入正式基线。

**为什么这样改**

性能优化需要能重复的同输入对照，也需要先知道时间花在哪里。正式 benchmark 回答“整体有没有更快”，projection profile 回答“reference 的投影里哪部分更慢”；二者分开，避免 profiling overhead 污染结论。

**基线与瓶颈发现**

后续用于 fused 对照的 reference 运行在 RTX 5060 Laptop GPU、PyTorch 2.9.1+cu128 上，batch=1、prompt=20 tokens、生成 32 tokens、正式迭代 5 次：

| 指标 | Reference P50 |
| --- | ---: |
| TTFT | 274.08 ms |
| Prefill 吞吐 | 72.97 tokens/s |
| Decode 单 token 延迟 | 161.04 ms |
| Decode 吞吐 | 6.21 tokens/s |
| 端到端延迟 | 5282.80 ms |
| 端到端生成吞吐 | 6.06 tokens/s |
| 峰值 allocated / reserved | 6.34 / 6.38 GiB |

reference projection profile 显示，decode 每层七类投影的反量化中位数合计约 5.17 ms，矩阵乘约 0.24 ms；gate/up/down 是反量化开销最大的三类投影。每次前向还会创建约 4–24 MiB 的 FP16 临时权重。该结果指出了可尝试的优化方向：减少每个 token、每层重复解包并写出完整权重的成本。

**复盘要点**

profile 只能解释被测实现的耗时分布，不能预先代表优化后系统的瓶颈。带 hook 的端到端数值明显比无 profiler 基线慢，因此后续比较一律使用 profiler 关闭的正式报告。

### 记录三：为 decode 和 prefill 增加 GPTQ Triton 融合路径

- 时间：2026-10-18
- 代码状态：当前工作区实现，尚无独立提交
- 主要代码：[gptq_kernels.py](../../src/myvllm/layers/gptq_kernels.py)、[gptq.py](../../src/myvllm/layers/gptq.py)、[qwen3.py](../../src/myvllm/models/qwen3.py)、[model_runner.py](../../src/myvllm/engine/model_runner.py)
- 性能结果：[fused baseline](../../benchmark/qwen/qwen3-1.7B-gptq-INT8/results/performance/fused/run-20261018T074030Z/baseline.md)

**遇到的问题**

reference 路径在每次 `GPTQLinear.forward()` 中解包整块投影权重，再调用 `F.linear`。decode 每次只处理很少的 activation 行，却重复为全部投影生成 FP16 权重；profile 显示这部分成本显著高于矩阵乘本身。

**改动内容**

- 保留 reference 后端，并增加 `fused`、`fused_decode`、`fused_prefill` 可选后端，便于回退和逐路径测试。
- Triton kernel 直接读取 packed qweight 与 group scales，在 tile 内解包、应用 zero point/scale 并累加，不再先构造完整的 FP16 权重矩阵。
- decode 使用 GEMV 形态，面向少量输入行；prefill 使用二维 GEMM 形态，面向多 token。两者共享已验证的 packed layout，但采用不同计算组织。
- 自动 fused 后端通过 `Context.is_prefill` 选择 kernel，避免仅凭输入长度猜模式；显式 `fused_decode` / `fused_prefill` 方便单独验证。
- kernel 当前沿用 checkpoint 约束：低字节优先、zero point 128、group size 128、FP16 输入和 scales；累加后输出与 `F.linear` 一致的形状和 dtype。

**为什么这样改**

decode 和 prefill 的矩阵形状不同：decode 更接近 GEMV，主要处理一个或少量 token；prefill 是多行矩阵乘。分开设计避免用同一 tile 配置勉强覆盖两种工作负载。kernel 在计算时消费量化权重，则可以绕开 reference 中反复生成完整权重临时张量的步骤。

**实测成果**

reference 与 fused 使用相同 GPU、模型、tokenized prompt、batch、生成长度和采样配置，各有 5 次正式迭代。此轮 fused 的 P50 结果为：

| 指标 | Reference | Fused | 变化 |
| --- | ---: | ---: | ---: |
| TTFT | 274.08 ms | 105.52 ms | 降低 61.5% |
| Prefill 吞吐 | 72.97 tokens/s | 189.54 tokens/s | 约 2.60 倍 |
| Decode 单 token 延迟 | 161.04 ms | 85.87 ms | 降低 46.7% |
| Decode 吞吐 | 6.21 tokens/s | 11.65 tokens/s | 约 1.88 倍 |
| 端到端延迟 | 5282.80 ms | 2770.04 ms | 降低 47.6% |
| 端到端生成吞吐 | 6.06 tokens/s | 11.55 tokens/s | 约 1.91 倍 |
| 峰值 allocated / reserved | 6.34 / 6.38 GiB | 6.32 / 6.35 GiB | 基本持平 |
| KV cache blocks | 138 | 141 | 增加 3 blocks |

这些数据说明在当前单请求、小 prompt workload 下，融合路径有明显端到端收益，且峰值显存没有增加。性能报告各为 5 次正式迭代，属于当前这次机器和 workload 的结果；要据此决定长期默认值，还应增加重复轮次并覆盖更长 prompt、batch 2/4 等实际目标场景。

### 记录四：增加固定输入的融合后端正确性评估

- 时间：2026-10-18
- 代码：[verify_gptq_backends.py](../../benchmark/qwen/qwen3-1.7B-gptq-INT8/correctness/verify_gptq_backends.py)、[test_gptq_correctness.py](../../tests/test_gptq_correctness.py)
- 运行报告：[backend correctness](../../benchmark/qwen/qwen3-1.7B-gptq-INT8/results/correctness/fused/run-20261018-182357-660398/backend-correctness-20261018-182357-660398.md)

**遇到的问题**

性能提升只有在计算结果可靠时才有意义。单纯比较生成文本会受到采样和 token 分叉影响，即使数值误差已存在，也难以定位从哪一层开始偏离。

**改动内容**

- reference 和 candidate 在独立子进程中顺序运行，避免 8GB 显存同时驻留两份模型。
- reference 生成固定 greedy token prefix；candidate 使用完全相同的 prompt token IDs 和 decode token IDs，逐步比较 prefill/decode logits。
- 在 reference 前向期间，对每个 GPTQ 投影的同一个 activation 立即运行 candidate kernel，比较投影输出，减少误差定位到整模型结果的困难。
- 报告 max/mean absolute error、RMS 与相对 RMS、allclose rate、Top-1 一致率、total variation、KL，以及逐投影误差和通过阈值。
- 增加合成输入和指标函数测试；GPU kernel 的真实权重比较仍需要 CUDA 设备运行。

**为什么这样改**

固定 token prefix 能让两个后端比较同一组计算状态，不会因早期 token 选择不同而把后续差异混在一起。逐投影的同输入比较定位局部算术误差，整模型 logits 与分布指标确认这些误差是否影响最终输出分布。

**正确性结果**

使用 20-token prompt、4 个 teacher-forced decode 步骤，对照阈值为单元素 `abs(error) <= 0.1 + 0.02 * abs(reference)`、logits allclose rate 至少 99.9%、Top-1 一致率至少 99%、平均 KL 不超过 1e-3、投影 allclose rate 至少 99.9%。实际报告中：

- Prefill logits：max absolute error 0.0664，allclose 和 Top-1 一致率均为 100%。
- Decode logits：max absolute error 0.1152，allclose 和 Top-1 一致率均为 100%；平均 KL 约 `2.01e-5`，平均 total variation 约 `1.29e-3`。
- 同输入投影比较：196 个 prefill 样本、784 个 decode 样本均通过；最差相对 RMS 误差分别约 `3.85e-4` 和 `1.25e-3`。
- 整体正确性评估通过。

这证明当前 checkpoint、prompt 和测试步数下 fused 输出满足设定容差，并不等同于已经覆盖所有上下文长度、batch、硬件或其他 GPTQ 格式。

- Nsight 结果：[kernel summary](../../benchmark/qwen/qwen3-1.7B-gptq-INT8/results/system-profile/fused/nsys-final/run-20261018-2320/nsys-summary.md)

**改动内容**

- 将 benchmark 按 performance、operator-profile、system-profile、correctness 分目录，所有运行结果改为带时间戳的独立目录，历史报告保留并校正链接。
- 新增 fused 整体路径 profiler：记录 prefill/decode 的 host wall、CUDA stream event 时间、GPU 显存、token IDs、git/software 元数据，以及每个 GPTQ projection 的 CUDA event 粗粒度归因。
- 检查 PyTorch trace 是否实际包含 CUDA device activity。当前环境的 CUPTI 报 `CUPTI_ERROR_INVALID_DEVICE`，报告将 device time 标成 unavailable，不把 0 当成真实耗时。
- 新增 Nsight Systems 入口；关闭进程内 PyTorch profiler 后可以捕获真实 CUDA kernel timeline。

**实测结果**

同一模型、prompt=20、batch=1、生成 32 tokens、正式迭代 5 次：

| 指标 | Reference P50 | Fused P50 | 变化 |
| --- | ---: | ---: | ---: |
| TTFT | 221.62 ms | 72.32 ms | 降低 67.4% |
| Decode 单 token 延迟 | 157.26 ms | 54.67 ms | 降低 65.2% |
| 端到端延迟 | 5070.40 ms | 1757.01 ms | 降低 65.3% |
| 峰值 allocated | 6.34 GiB | 6.32 GiB | 基本持平 |

Nsight 短 trace 中，`_gptq_prefill_kernel` 占捕获到的 kernel device time 83.7%，`_gptq_decode_kernel` 占 4.1%。该 trace 包含初始化和 warmup，百分比用于识别 kernel 是否执行及粗略热点，不替代正式端到端 benchmark。

## 当前阶段总结

已经完成的主线是：严格接入一个可运行的 Qwen3 GPTQ-INT8 checkpoint，建立 reference benchmark 和投影 profile，针对反量化开销增加 decode/prefill 融合 kernel，并用逐投影及整模型 logits 对照验证当前实现。当前 fused 在既有 batch=1、20-token prompt、32-token generation 实验中约提升端到端吞吐 1.91 倍，正确性报告通过。

接下来应补足性能结果的重复性和工作负载覆盖：至少增加正式迭代次数，并覆盖 prefill 128/512 tokens、batch 2/4 和更长 decode。当前 fused 已通过现有正确性阈值并在 batch=1 目标 workload 上明显改善，但还需要确认这些收益在更大输入下是否稳定。PyTorch CUPTI activity 仍受环境限制，必要时继续使用无 in-process profiler 的 Nsight Systems 捕获做 kernel 归因。
