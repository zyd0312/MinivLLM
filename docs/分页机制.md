> KV Cache 预先申请成一个由固定大小物理块组成的大池子；每条序列只维护一张逻辑块表。写入时通过 `slot_mapping` 找到物理槽位，读取时通过 `block_tables` 将逻辑位置翻译成物理块位置。

它解决的是动态批处理时序列长度不同、不断增长，以及物理内存不连续的问题。

---

### 1. 整体内存布局

在 [`model_runner.py`](/src/myvllm/engine/model_runner.py) 中，项目一次性申请整个 KV Cache 池：

```python
allocated_kv_cache = torch.zeros(
    2,
    num_layers,
    max_cached_blocks,
    block_size,
    num_kv_heads,
    head_dim,
)
```

逻辑形状是：

```text
[2, num_layers, num_physical_blocks, block_size, num_kv_heads, head_dim]
```

第一维的 `2` 分别是 K 和 V。随后每一层的 Attention 模块获得自己对应的切片：

```python
module.k_cache = allocated_kv_cache[0, layer_id]
module.v_cache = allocated_kv_cache[1, layer_id]
```

所以单层看到的 cache 形状为：

```text
[num_physical_blocks, block_size, num_kv_heads, head_dim]
```

一个物理块可以容纳 `block_size` 个 token。比如：

```text
block_size = 16
physical block 3
    token slot 0
    token slot 1
    ...
    token slot 15
```

物理块不属于某条固定序列。它由 `BlockManager` 动态分配给不同序列。

### 2. 逻辑块和物理块

假设一条序列有 35 个 token，`block_size = 16`：

```text
逻辑块 0: token  0 ~ 15
逻辑块 1: token 16 ~ 31
逻辑块 2: token 32 ~ 34
```

它可能被分配到不连续的物理块：

```text
逻辑块 0 -> 物理块 7
逻辑块 1 -> 物理块 2
逻辑块 2 -> 物理块 11
```

序列中的 `block_table` 保存的就是：

```python
[7, 2, 11]
```

也就是：

```text
block_table[logical_block_id] = physical_block_id
```

这张表由 [`BlockManager`](src/myvllm/engine/block_manager.py:28) 管理，最终通过 `prepare_prefill()` 或 `prepare_decode()` 转换成 GPU 上的 `block_tables`。

由于 batch 中不同序列的块数不同，runner 会补齐为矩阵：

```text
[batch_size, max_num_blocks]
```

不足的位置填 `-1`：

```text
sequence A: [7, 2, 11, -1]
sequence B: [4, 9, -1, -1]
```

---

### 3. 写入路径：`slot_mapping`

写入 KV Cache 的入口是：

```python
store_kvcache(...)
```

对应内核是 [`store_kvcache_kernel`](src/myvllm/layers/attention.py:13)。

它的输入 K/V 是连续 token：

```text
key: [num_tokens, num_kv_heads, head_dim]
value: [num_tokens, num_kv_heads, head_dim]
```

而 `slot_mapping` 给每个 token 指定一个全局物理槽位：

```text
slot_mapping[token_index] = physical_block_id * block_size + offset_in_block
```

内核先拆分槽位：

```python
block_idx = slot_idx // block_size
block_offset = slot_idx % block_size
```

例如：

```text
slot_idx = 37
block_size = 16

block_idx    = 37 // 16 = 2
block_offset = 37 % 16  = 5
```

也就是把 token 写入：

```text
物理块 2 的第 5 个 token 槽位
```

最终地址对应：

```python
cache[
    block_idx,
    block_offset,
    head_idx,
    head_offset
]
```

K 和 V 使用相同地址分别写入两个 cache。

内核的并行网格是：

```text
(num_tokens, num_kv_heads)
```

每个 Triton program 负责一个：

```text
(token, kv_head)
```

组合，因此同一 token 的所有 KV 头可以并行写入。

`slot_idx == -1` 时直接跳过：

```python
if slot_idx == -1:
    return
```

这允许 batch padding 或 CUDA Graph 中未使用的位置不修改 cache。

### 4. Prefill 阶段如何构造写入位置

prefill 时，输入通常是多条不同长度的 prompt 拼接成一个一维 token 张量。

`prepare_prefill()` 会遍历每条序列，并为需要新计算的 token 生成 slot：

```python
slot_mappings.extend(
    range(block_id * block_size,
          (block_id + 1) * block_size)
)
```

最后一个不满的块只生成实际 token 数量：

```python
range(
    block_id * block_size,
    block_id * block_size + seq.last_block_num_tokens
)
```

例如：

```text
block_size = 4
序列长度 = 6
block_table = [7, 2]

slot_mapping =
[28, 29, 30, 31, 8, 9]
```

这里：

```text
逻辑块 0 -> 物理块 7 -> slot 28~31
逻辑块 1 -> 物理块 2 -> slot 8~9
```

虽然输入 token 在内存中是连续的，但它们会按照 `slot_mapping` 分散写入物理 cache。

Attention 的 forward 首先写 cache：

```python
store_kvcache(
    k_to_store,
    v_to_store,
    k_cache,
    v_cache,
    context.slot_mapping,
    self.block_size,
)
```

然后 prefill 使用 Flash Attention 计算当前 prompt 内部的注意力。

### 5. Decode 阶段如何追加新 token

decode 时每条序列每次只输入一个新 token。

`prepare_decode()` 为每条序列设置：

```python
slot_mappings.append(
    seq.block_table[-1] * self.block_size
    + seq.last_block_num_tokens - 1
)
```

含义是：

```text
把当前新 token 写入最后一个逻辑块的下一个物理槽位
```

假设：

```text
block_size = 4
block_table = [7, 2]
当前序列长度 = 6
```

当前最后一个块物理编号为 2，块内已有两个 token，因此新 token 写到：

```text
slot = 2 * 4 + 2 = 10
```

注意，`context_lens` 表示的是写入前已有的上下文长度。decode 内核用它决定本次要读取多少历史 token。

序列追加到新块边界时，`BlockManager.append()` 会分配新的物理块：

```python
elif seq.num_tokens % self.block_size == 1:
    block = self._allocate_block(self.free_block_ids[0])
    block_tables.append(block.block_id)
```

因此序列增长过程中只在跨越块边界时申请新物理块。

### 6. Decode 读取路径：`block_tables`

decode 使用：

```python
paged_attention_decode(...)
```

内核网格为：

```text
(batch_size, num_heads)
```

每个 program 处理一个：

```text
(batch 中的序列, query head)
```

首先读取该序列的上下文长度：

```python
context_len = tl.load(context_lens_ptr + batch_idx)
```

然后把历史 token 按 chunk 遍历。对每个 token 的逻辑位置 `offs_n`：

```python
logical_block = offs_n // block_size
offs_in_block = offs_n % block_size
```

例如：

```text
token position = 21
block_size = 16

logical_block = 1
offset        = 5
```

然后通过块表查找物理块：

```python
physical_block = tl.load(
    block_tables_ptr
    + batch_idx * max_num_blocks
    + logical_block
)
```

如果：

```text
block_tables[batch_idx] = [7, 2, 11]
```

那么逻辑位置 21 会被翻译为：

```text
logical block 1 -> physical block 2
block offset   5
```

最终 cache 地址由以下公式计算：

```python
kv_offset = (
    physical_block * block_size * num_kv_heads * head_dim
    + offs_in_block * num_kv_heads * head_dim
    + kv_head_idx * head_dim
    + offs_d
)
```

对应：

```text
cache[
    physical_block,
    offs_in_block,
    kv_head_idx,
    head_dim_offset
]
```

这一步是分页机制最关键的地方：逻辑 token 位置连续，但对应的物理块可以完全不连续。

### 7. 一个 chunk 可以跨越多个物理块

内核没有假设一个 chunk 对应一个物理块。

例如：

```text
block_size = 16
BLOCK_N = 64
```

一个长度为 64 的 chunk 可能覆盖：

```text
逻辑块 0、1、2、3
```

它会对每个 lane 单独计算：

```python
logical_block = offs_n // block_size
offs_in_block = offs_n % block_size
```

因此即使：

```text
逻辑块 0 -> 物理块 7
逻辑块 1 -> 物理块 2
逻辑块 2 -> 物理块 11
逻辑块 3 -> 物理块 4
```

仍然可以在同一个 Triton chunk 中读取，不需要物理内存连续。

### 8. `-1` padding 和 mask

batch 中的序列长度不同，因此 `block_tables` 要填充：

```text
[7, 2, 11]
[4, 9, -1]
```

内核通过：

```python
in_range = (
    (offs_n < context_len)
    & (logical_block < max_num_blocks)
)
```

并进一步判断物理块是否存在：

```python
valid = in_range & (physical_block != -1)
```

无效位置的 Key、Value 不参与计算：

```python
k = tl.load(..., mask=valid[None, :], other=0.0)
v = tl.load(..., mask=valid[None, :], other=0.0)
qk = tl.where(valid, score, -1e10)
```

`physical_block` 对无效 lane 会被替换为 0：

```python
physical_block = tl.where(valid, physical_block, 0)
```

这样做是为了让地址计算本身保持在合法范围内，真正的数据访问则由 mask 禁止。

### 9. Prefill 和 Decode 的分页差异

这个实现将两个阶段分开：

| 阶段 | KV 写入 | 注意力读取 |
|---|---|---|
| Prefill | 通过 `slot_mapping` 写入分页 cache | Flash Attention 直接读取当前连续的 `q/k/v` |
| Decode | 通过 `slot_mapping` 写入新 token | Paged Attention 通过 `block_tables` 读取历史 cache |

在 `Attention.forward()` 中，顺序是：

```python
store_kvcache(...)
```

然后：

```python
if context.is_prefill:
    flash_attention_prefill(...)
else:
    paged_attention_decode(...)
```

因此 decode 的当前 token 会先写入 cache，再用 `context_lens` 读取完整上下文。这意味着 decode 时的 `context_lens` 应当包含当前写入后的有效长度；runner 中使用：

```python
context_lens.append(len(seq))
```

而 `seq` 已经包含调度阶段追加的 token。

### 10. 分页池的分配和回收

`BlockManager` 维护：

```python
free_block_ids
used_block_ids
```

分配时：

```python
block = self._allocate_block(self.free_block_ids[0])
```

回收时：

```python
block.ref_count -= 1
if block.ref_count == 0:
    self._deallocate_block(block_id)
```

序列结束或被抢占时，其 `block_table` 中的所有物理块都会释放。

这带来两个实际效果：

1. 每条序列不需要申请一段连续的 KV 内存。
2. 新序列可以复用旧序列释放的物理块。

这也是分页 cache 能支持动态 batch 的原因。

---

### 11. GQA/MQA 下的额外映射

如果 Query 头数量大于 KV 头数量：

```python
kv_head_idx = head_idx // (num_heads // num_kv_heads)
```

例如：

```text
num_heads = 32
num_kv_heads = 8
```

每 4 个 Query 头共享一个 KV 头：

```text
Q head 0~3   -> KV head 0
Q head 4~7   -> KV head 1
...
```

分页地址中的头维度使用 `kv_head_idx`，所以 cache 只需要保存 8 个 KV 头，而不是 32 个，降低了显存占用。

### 12. 这份实现的边界

这份代码已经实现了“物理 KV 池 + 逻辑块表 + slot 写入 + paged decode 读取”的核心分页机制，但需要注意：

- `block_tables` 主要在 decode 内核中真正用于读取。
- prefill 的 Flash Attention 直接使用当前 `q/k/v`，并没有通过历史 `block_tables` 读取已缓存前缀。
- 因此 prefix cache 的复用能力受到限制，不能简单认为所有 `num_cached_tokens` 都已经被 prefill 正确消费。
- `block_size` 同时影响显存碎片、块表长度和地址计算；块越大，块表开销越小，但最后一个块的内部浪费可能越多。
- `max_cached_blocks` 是所有序列共享的总物理块数量，不是每条序列独占的数量。

核心数据流可以概括为：

```text
Sequence.block_table
        |
        v
block_tables[batch, logical_block]
        |
        v
logical token position
        |
        +--> logical_block = token // block_size
        +--> offset        = token % block_size
        |
        v
physical_block = block_tables[batch, logical_block]
        |
        v
K/V cache[physical_block, offset, kv_head, head_dim]
```

写入方向则是：

```text
当前 token 的 K/V
        |
        v
slot_mapping[token]
        |
        +--> physical_block = slot // block_size
        +--> offset          = slot % block_size
        |
        v
K/V cache[physical_block, offset]
```
